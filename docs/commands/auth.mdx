---
title: "teaway auth: Install the Narrow Passwordless Helper"
sidebarTitle: "Auth"
description: "Inspect, install, or remove the narrow per-user passwordless helper that lets teaway run privilege mutations without repeated password prompts."
---

By default, teaway uses ordinary `sudo` whenever it needs to write a power setting or schedule a shutdown — just as you would run any other privileged command. The `teaway auth` subcommands let you go further: install a narrow, root-owned per-user helper that restricts exactly which privileged operations are allowed and removes the need to re-enter your password on every mutation. You can also inspect registration state at any time, and fully remove the helper when you no longer need it.

<Note>
Use registered mode only on a **trusted single-user account**. After registration, any process running as your macOS user can perform the delegated teaway operations without a password. Shared or untrusted accounts should continue using ordinary `sudo` mode — the helper provides convenience, not broader security isolation.
</Note>

## teaway auth status

`teaway auth status` shows whether the per-user helper is installed, whether the installed version matches the running teaway version, and whether sudo Touch ID is configured for your account.

```bash
teaway auth status
```

### Example output — registered

```text
authorization: registered
helper version: 1.2.0
mode: passwordless narrow helper
touch id for sudo: configured
```

### Example output — unregistered

```text
authorization: unregistered
mode: ordinary sudo with the system credential cache
touch id for sudo: not configured
touch id note: macOS PAM controls this; teaway does not modify PAM
```

### Registration status values

<ParamField body="unregistered" type="string">
  Neither the helper binary nor the sudoers rule is present. teaway will use ordinary `sudo` for privileged operations.
</ParamField>

<ParamField body="registered" type="string">
  The helper is installed, root-owned, version-matched, and the sudoers rule is in place. Privileged mutations run without a password prompt.
</ParamField>

<ParamField body="needs-repair" type="string">
  Installation is partial, the helper version does not match the running teaway version, the helper binary is unauthorised, or the sudoers rule is stale. Re-run `teaway auth register` to repair. This state commonly appears after a `brew upgrade teaway`.
</ParamField>

<Note>
`teaway auth status` is read-only. It never modifies PAM configuration, never changes the sudoers file, and never requests administrator authorization.
</Note>

## teaway auth register

`teaway auth register` sets up the narrow passwordless helper. It installs two files using a single visible administrator authorization:

```text
/Library/PrivilegedHelperTools/com.soundadam.teaway.helper.<uid>
/etc/sudoers.d/soundadam-teaway-<uid>
```

```bash
teaway auth register
```

### What register installs

The helper binary is a root-owned copy of the exact `teaway` executable that performed registration. The sudoers rule is validated before **and** after installation. The rule permits only these operations — nothing else:

- Set `disablesleep` to `0` or `1`
- Schedule one canonical teaway shutdown event
- Cancel one canonical teaway or legacy shutdown event

The helper validates exact argument arity, an allowlisted operation name, a canonical date format, and a bounded owner prefix and identifier. It then invokes `/usr/bin/pmset` directly without a shell. Any unsupported, malformed, or extra argument fails closed. The rule does not permit arbitrary CLI commands, arbitrary `pmset` arguments, or a shell.

### Password entry

Before invoking `sudo`, teaway explains that the macOS password prompt is handled entirely by `sudo` — the entry field is hidden, and teaway never reads, logs, or stores your password. This explanation appears in the terminal so you know what to expect before the prompt appears.

### Example output

```text
Set up passwordless Teaway controls
  macOS will ask for your account password once.
  Password input is hidden; no characters appear while you type.
  Teaway never reads or stores your password.
  After setup, only awake-mode and teaway-owned shutdown operations run without a password.
✓ Passwordless Teaway controls are ready.
  Helper version: 1.2.0
  Helper: /Library/PrivilegedHelperTools/com.soundadam.teaway.helper.501
  Sudoers rule: /etc/sudoers.d/soundadam-teaway-501
  Scope: awake mode and teaway-owned shutdown operations only
  This permission is available to processes running as this macOS user.
```

### When to re-register

Re-run `teaway auth register` after upgrading teaway if `teaway auth status` reports `needs-repair` or a version mismatch. The registration replaces the helper binary after a new visible administrator check.

<Tip>
The interactive TUI client also surfaces registration state in its guided menu. If passwordless controls are absent or need repair, the menu offers a one-step setup action directly — you do not need to drop to the command line.
</Tip>

## teaway auth unregister

`teaway auth unregister` removes the helper binary and the sudoers rule using ordinary administrator authorization. After unregistering, teaway falls back to ordinary `sudo` for all privileged operations.

```bash
teaway auth unregister
```

### Example output

```text
authorization: unregistered
```

`unregister` does not affect any active `teaway on` ownership record or any scheduled shutdown. Your current awake state and shutdown schedule remain exactly as they are — only the authorization mechanism changes.

<Warning>
After unregistering, the next `teaway on`, `teaway off`, or `teaway shutdown` command will prompt for your administrator password via ordinary `sudo`. Make sure you have interactive access to the terminal before unregistering on a remote session.
</Warning>
