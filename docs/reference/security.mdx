teaway is a narrowly scoped command-line tool: it changes one macOS power setting when you explicitly ask it to, and it restores exactly what it changed. Every security decision flows from that boundary. Read this page to understand what trust you extend when you install teaway, and what it deliberately refuses to do.

## What teaway does and does not do

teaway has no network listener, no cloud service, no telemetry, no workload inspection, no password cache, no setuid executable, and no always-running daemon. It activates only when you run an explicit command.

Most importantly, teaway **never reads, stores, logs, or pipes your administrator password**. When macOS presents an authentication dialog, that exchange belongs entirely to macOS — teaway only triggers it and waits for the result. All privileged operations use fixed, well-known macOS system paths (`/usr/bin/pmset`), never arbitrary shell commands.

Read-only commands — `teaway status` and `teaway version` — are strictly non-mutating. They cannot modify power settings or cancel scheduled events.

<Note>
  The `teaway auth register` command will tell you explicitly, before invoking `sudo`, that the one-time password entry is hidden and is never read or stored by teaway.
</Note>

## Awake ownership transaction

When you run `teaway on`, teaway performs a four-step owned transaction:

1. Inspect the current macOS sleep setting.
2. Persist the exact pre-change value in private, restricted state storage.
3. Authorize and apply `disablesleep=1` through a single fixed privileged operation.
4. Re-read macOS state and report success only after the live value is verified.

State files are stored in an atomic mode-0700 directory using mode-0600 files. If any step fails, teaway retains a recovery phase rather than silently claiming ownership of a state it does not actually own.

When you run `teaway off`, it restores only the value it previously recorded. If the live `disablesleep` value is `1` but there is no matching teaway ownership record, teaway leaves it alone — that setting belongs to something else, and teaway will not silently undo external policy.

<Info>
  Corrupt, conflicting, or unsupported state always fails closed. teaway will not guess at what to restore.
</Info>

## Shutdown boundary

Scheduled shutdowns use a separate, independent transaction. `teaway shutdown after` accepts only bounded explicit durations — between 10 minutes and 7 days — and prints the absolute deadline, timezone, hostname, owner, and action ID before committing.

Before and after scheduling, teaway reads `/usr/bin/pmset -g sched` directly. It rejects existing shutdowns or conflicting owners, persists the exact event tuple before any system call, verifies the scheduled event in macOS state, and attempts exact compensation if a later commit step fails. On macOS 26, four-digit year rendering in pmset output is normalized before comparison against the stored two-digit canonical tuple.

`teaway shutdown cancel` removes only the exact owned event — it never runs `pmset cancelall` and never touches unrelated Apple wake or sleep events. Shutdown ownership is independent of awake ownership: `teaway off` never silently cancels a pending shutdown.

## Registered helper scope

`teaway auth register` installs two root-owned, per-user artifacts:

- `/Library/PrivilegedHelperTools/com.soundadam.teaway.helper.<uid>`
- `/etc/sudoers.d/soundadam-teaway-<uid>`

The sudoers rule delegates **only** the following operations:

- `disablesleep` values `0` and `1`
- One canonical shutdown schedule
- Exact cancellation of a canonical or recorded legacy event
- Helper version inspection

The rule does **not** delegate the public CLI, a shell, arbitrary executables, or arbitrary `pmset` arguments. Before invoking `/usr/bin/pmset`, the helper validates operation name, argument count, date format, owner prefix, identifier character set, and identifier length.

<Warning>
  The sudoers rule trusts the entire macOS user account. Any process running as that user can invoke the allowlisted operations. Do not register the helper on a shared or untrusted account.
</Warning>

A version mismatch between the installed helper and the current teaway binary **fails closed** — privileged operations will not proceed until you re-run `teaway auth register` to refresh the helper.

## Installation and supply chain

The canonical repository, Homebrew Formula token, Go module, and executable name are all `teaway`. Homebrew installs no `tea` or `tea-away` command.

The Homebrew Formula builds teaway from source and verifies the exact SHA-256 of the immutable source archive. Public releases do not ship prebuilt, unnotarized executables. Any future prebuilt binary would require Developer ID signing, timestamping, Apple notarization, and verification of the final immutable asset before distribution.

<Tip>
  After a `brew upgrade teaway`, run `teaway auth status` to confirm the helper version matches the new binary. If there is a mismatch, run `teaway auth register` to refresh it.
</Tip>

## Vulnerability reporting

<Warning>
  Do **not** file a public GitHub issue to report a suspected security vulnerability. Doing so publishes potential exploit details before a fix is available.
</Warning>

Use GitHub's **Report a vulnerability** form in the repository Security tab. This creates a private security advisory visible only to the maintainer. Include the affected teaway version, your macOS version and architecture, your authorization mode (ordinary sudo or registered helper), reproduction steps, expected and observed behavior, and the security impact. Do not include administrator passwords, private keys, access tokens, or unrelated secrets.

Reports are evaluated against the boundaries described on this page. Public disclosure should wait until a fix or coordinated advisory is ready. Full details are in [SECURITY.md](https://github.com/soundadam/teaway/blob/main/SECURITY.md).
