teaway requires administrator privileges only for the operations that change macOS sleep behavior or create and cancel a delayed shutdown. Read-only commands — `teaway status`, `teaway shutdown status`, `teaway auth status`, and `teaway version` — run without any elevated access. For privileged mutations, teaway offers two modes: ordinary sudo, which is the default, and an optional registered helper that removes repeated password prompts after a single one-time setup.

<Note>
  teaway never reads, stores, transmits, or logs an administrator password in either mode. The one visible macOS password prompt you see during registration is handled entirely by `sudo`; teaway has no access to what you type.
</Note>

## Two authorization modes

### Ordinary sudo

Without registration, every privileged mutation follows this sequence:

1. teaway runs `sudo -v` interactively, refreshing the system credential timestamp.
2. teaway invokes one fixed `/usr/bin/pmset` operation through `sudo`.
3. teaway reads the resulting macOS state and verifies the change before committing.

This mode works on any Mac without any setup. Touch ID is available during the `sudo` prompt if your administrator has enabled `pam_tid.so` for sudo — teaway detects and reports that configuration in `teaway auth status` but never modifies PAM itself. teaway also never calls `sudo -k`, so it does not invalidate an existing credential timestamp.

### Registered helper

`teaway auth register` installs two root-owned, per-user files after a single visible administrator authorization:

- `/Library/PrivilegedHelperTools/com.soundadam.teaway.helper.<uid>`
- `/etc/sudoers.d/soundadam-teaway-<uid>`

The helper is a root-owned copy of the exact teaway executable that performed registration. The sudoers rule is validated before and after installation. Once installed, allowed mutations use `sudo -n` and do not prompt for a password or Touch ID as long as the helper remains healthy and version-matched.

## When to use each mode

| Situation | Recommended mode |
|---|---|
| Trusted single-user Mac | Registered helper |
| Shared or multi-user Mac | Ordinary sudo |
| Untrusted account | Ordinary sudo |
| Automated or scripted use on a personal machine | Registered helper |

The sudoers rule grants permission to the macOS **account**, not to a specific terminal session or binary. Any process running as that user can invoke the allowlisted operations. Use registered mode only on an account you fully trust. Shared or untrusted accounts should stay in ordinary sudo mode.

## What the registered helper permits

The sudoers rule is intentionally narrow. It permits only the following operations:

```text
version
set-disablesleep 0
set-disablesleep 1
schedule-shutdown MM/DD/YY HH:MM:SS teaway:<identifier>
cancel-shutdown MM/DD/YY HH:MM:SS teaway:<identifier>
```

The helper validates exact argument count, the allowlisted operation name, canonical date format round-trips, the owner prefix, and a bounded ASCII alphanumeric/hyphen identifier before invoking `/usr/bin/pmset` without a shell. Unsupported, malformed, or extra arguments fail closed — the helper rejects them outright.

The rule does **not** permit:
- Arbitrary `pmset` arguments or flags
- A shell or arbitrary command execution
- Any teaway subcommand beyond the list above
- Any operation on behalf of a different user

## Register, inspect, and remove

<Steps>
  <Step title="Register the helper">
    Run the registration command. Before invoking `sudo`, teaway explains that the macOS password prompt is hidden and handled by `sudo`. Enter your administrator password when prompted — this is the one and only authorization event.

    ```sh
    teaway auth register
    ```

    After registration, teaway confirms the helper and sudoers rule are both in place.
  </Step>
  <Step title="Verify status">
    Check the current authorization state at any time:

    ```sh
    teaway auth status
    ```

    The status is one of three values:

    | Status | Meaning |
    |---|---|
    | `unregistered` | Both machine-level files are absent; ordinary sudo is in use |
    | `registered` | Helper is authorized and version-matched with the installed CLI |
    | `needs-repair` | Installation is partial, unauthorized, ignored, or version-mismatched |
  </Step>
  <Step title="Remove the helper">
    To remove the helper and its sudoers rule, run:

    ```sh
    teaway auth unregister
    ```

    Unregistration uses ordinary administrator authorization and removes both installed files. teaway returns to ordinary sudo mode.
  </Step>
</Steps>

## After an upgrade

An upgrade may produce a version mismatch between the CLI and the root helper. When `teaway auth status` reports `needs-repair`, re-run registration with visible administrator authorization to replace the helper:

```sh
teaway auth register
teaway auth status
```

teaway does not silently replace a root-owned helper during an upgrade. This is intentional: installing a new root file is a machine-level trust decision, and it stays visible. See the [Upgrade guide](/guides/upgrade) for the full upgrade procedure.

## Installed file paths

After registration, teaway installs exactly two files:

| Path | Description |
|---|---|
| `/Library/PrivilegedHelperTools/com.soundadam.teaway.helper.<uid>` | Root-owned copy of the teaway executable that performed registration |
| `/etc/sudoers.d/soundadam-teaway-<uid>` | Validated per-user sudoers rule permitting the narrow allowed operations |

Both files are root-owned. The `<uid>` suffix scopes them to your macOS user account, so multiple accounts on the same machine each maintain independent registrations.
