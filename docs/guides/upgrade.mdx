---
title: "Upgrade teaway via Homebrew and Refresh the Auth Helper"
sidebarTitle: "Upgrade"
description: "Upgrade teaway via Homebrew, check the helper version after install, and re-register when auth status reports a mismatch — safely and without disruption."
---

Upgrading teaway is a two-part process: update the CLI through Homebrew, then check whether the registered helper needs to be refreshed. Because teaway does not silently replace a root-owned file, a version mismatch between the CLI and the helper requires one explicit re-registration step. The upgrade does not affect your current awake state or any scheduled shutdown — those persist independently and remain in place while you upgrade.

<Steps>
  <Step title="Update Homebrew and upgrade teaway">
    Fetch the latest Formula index, then upgrade the package:

    ```sh
    brew update && brew upgrade teaway
    ```

    Homebrew builds teaway from the immutable GitHub source tag and verifies the archive SHA-256. No prebuilt binary is involved.
  </Step>
  <Step title="Confirm the installed version">
    Verify that the upgrade completed and check which version is now active:

    ```sh
    teaway version
    ```
  </Step>
  <Step title="Check authorization status">
    Inspect whether the registered helper matches the new CLI version:

    ```sh
    teaway auth status
    ```

    The three possible outcomes are:

    | Status | What it means | What to do |
    |---|---|---|
    | `registered` | Helper is present and version-matched | Nothing — you are done |
    | `needs-repair` | Helper version does not match the CLI, or installation is partial | Re-register (next step) |
    | `unregistered` | No helper is installed; ordinary sudo is in use | Nothing unless you want registered mode |
  </Step>
  <Step title="Re-register if status shows needs-repair">
    If `auth status` reports `needs-repair`, replace the helper with one visible administrator authorization:

    ```sh
    teaway auth register
    teaway auth status
    ```

    teaway explains before invoking `sudo` that the password prompt is hidden and handled by the system. After the single authorization event, the new root helper is in place and `auth status` returns `registered`.

    <Note>
      teaway intentionally does not replace a root-owned helper automatically during an upgrade. Installing a new root file is a machine-level trust decision and must stay visible. You choose when and whether to refresh it.
    </Note>
  </Step>
  <Step title="Confirm awake state is undisturbed">
    Check that your awake state and any scheduled shutdown survived the upgrade unchanged:

    ```sh
    teaway status
    teaway shutdown status
    ```

    Both should reflect exactly the state you had before upgrading. The upgrade touches only the CLI binary and, when you re-register, the helper file — it does not modify macOS power settings or scheduled events.
  </Step>
</Steps>

<Tip>
  If you run `teaway on` before upgrading, the owned awake state is recorded independently of the CLI binary. Upgrading the CLI does not clear or alter that record. You can upgrade safely while the Mac is serving workloads.
</Tip>
