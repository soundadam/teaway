teaway supplies the reversible power-control layer for a headless Mac, MacBook build box, Mac mini home server, homelab node, or long-running workstation. It keeps macOS from sleeping — including with the laptop lid closed — then restores the exact sleep setting it owned when you are done. Everything else in the availability stack — remote access, service supervision, backups, networking, and thermals — remains your responsibility to configure and test before you rely on the machine remotely.

## Pre-flight checklist

Work through every item below before running `teaway on`. Skipping any one of them can leave you locked out of an unattended machine with no safe recovery path.

<Steps>
  <Step title="Confirm macOS 13 or later">
    teaway requires macOS 13 Ventura or later on Apple silicon or Intel. Run `sw_vers -productVersion` to verify.
  </Step>
  <Step title="Test remote access from a second device">
    Remote Login (SSH), Screen Sharing, a VPN, or another access method must already be configured **and** tested from a separate device before you close a lid or walk away. Do not assume it works — confirm it.
  </Step>
  <Step title="Verify workloads start independently of the terminal">
    Any service that must survive the end of your session needs to launch through launchd, a CI runner, a service manager, or a documented manual procedure. A process that only runs inside your terminal will stop when that terminal closes, regardless of sleep state.
  </Step>
  <Step title="Place the Mac on a hard, open, ventilated surface">
    Set the Mac on a desk, shelf, or rack position where airflow is unrestricted. Never run it closed inside a bag, drawer, or other confined space.

    <Warning>
      A MacBook has significantly less thermal headroom with its lid closed than in normal open use. Sustained workloads in a confined or poorly ventilated location risk hardware damage. teaway does not override thermal protection — physical placement is your responsibility.
    </Warning>

    <Tip>
      Connect the Mac to AC power for unattended use. teaway works the same on battery or AC, but a battery can drain silently during a long session, leaving the machine unreachable. A UPS further improves availability for critical setups, though it is outside teaway's scope.
    </Tip>
  </Step>
  <Step title="Understand your backups, monitoring, and network recovery">
    Know how backups run, where alerts go, and what happens if the machine loses network connectivity or restarts unexpectedly. Put those systems in place and test them before relying on the Mac remotely.
  </Step>
  <Step title="Confirm no other tool owns disablesleep">
    teaway records ownership of the `disablesleep` setting and refuses to adopt a live value it did not set. If another tool already controls that setting, decide which one owns it before proceeding.
  </Step>
</Steps>

## Initial setup

Install teaway, then inspect the baseline state before changing anything. Reading the current values first ensures teaway captures the correct pre-change snapshot when you run `teaway on`.

```sh
brew install soundadam/tap/teaway
teaway version
teaway auth status
teaway status
```

For a trusted single-user account, register the narrow privileged helper once. Registration requires one visible administrator authorization, after which teaway's allowed power operations run without a password prompt.

```sh
teaway auth register
teaway auth status
```

The helper is a root-owned per-user file — it does not create a daemon, network listener, or background process. See the [Authorization guide](/guides/authorization) for the full explanation of what the helper permits and when to use it.

## Start server operation

Enable awake mode and verify the result:

```sh
teaway on
teaway status
```

A healthy status reports `Awake mode: On — managed by teaway` and `disablesleep=1`. The `status` output also shows your current power source; that value is informational. Before you close a laptop lid or leave the machine unattended, verify remote reachability one more time from your second device.

`teaway on` is idempotent — running it again does not create a duplicate ownership record or overwrite the saved baseline.

<Note>
  If you prefer a guided experience, run `teaway` with no arguments to open the interactive client. It walks through setup, status, and common actions without requiring you to remember every subcommand.
</Note>

## Schedule a delayed shutdown

To automatically shut down the Mac after a bounded delay, use `teaway shutdown after` with an explicit duration:

```sh
teaway shutdown after 2h
```

teaway resolves the duration to an absolute local deadline and prints it alongside the hostname, owner, and action ID. The schedule is committed only after macOS confirms the exact event. Durations accept `m`, `h`, and `d` units; the minimum is 10 minutes and the maximum is 7 days.

Inspect or cancel the scheduled shutdown at any time:

```sh
teaway shutdown status
teaway shutdown cancel
```

Only one teaway shutdown may exist at a time. `teaway shutdown cancel` removes only the exact teaway-owned event — it never touches Apple wake events or schedules owned by other software.

## Restore normal operation

When you are ready to return the Mac to its previous sleep behavior, run:

```sh
teaway off
teaway status
```

`teaway off` restores the exact `disablesleep` value that was in place before you ran `teaway on`. If there is no teaway-owned record, the command refuses to adopt or clear any live external value — it will not silently undo a setting owned by another tool or administrator.

## What teaway does not handle

Disabling sleep is one layer of server operation. teaway cannot guarantee or configure:

- **Network connectivity or remote login** — SSH, Screen Sharing, VPNs, and firewall rules are outside its scope.
- **Process startup, restart, or health supervision** — use launchd, a service manager, or a CI runner for that.
- **Filesystem integrity, backups, or storage capacity** — teaway has no visibility into your data or disk state.
- **Recovery from power loss, OS crashes, forced restarts, or hardware failure** — these are availability-stack concerns, not power-setting concerns.
- **Safe thermals in a confined location** — teaway does not override macOS thermal protection.
- **Uninterrupted operation during macOS updates** — a forced reboot will clear the awake state.

Use the smallest set of additional tools required for each of these responsibilities, and test failure recovery before you rely on the Mac remotely.

## Daily monitoring checklist

For an unattended or remote Mac, check the following regularly:

- **`teaway status`** — confirm awake mode is on and ownership is intact.
- **`teaway auth status`** — confirm the helper is healthy and version-matched.
- **Power source and battery health** — ensure AC is still connected.
- **Thermal state and physical ventilation** — verify the machine is not in a confined space.
- **Free disk space and backup freshness** — a full disk can silently break workloads.
- **Remote-access reachability** — test SSH or Screen Sharing from your second device.
- **Service health and restart behavior** — check that supervised processes are running.
- **Pending macOS maintenance or reboot requirements** — an unattended update can restart the machine.

teaway has no polling daemon or telemetry. If you integrate `teaway status` output into a monitoring system, ensure that system can handle command failure gracefully and distinguish between `off`, `external`, and recovery states.

## Upgrade procedure

When a new version of teaway is available, upgrade through Homebrew and verify the helper still matches the CLI:

```sh
brew update && brew upgrade teaway
teaway version
teaway auth status
```

If `auth status` reports `needs-repair`, the helper version no longer matches the CLI. Re-register with one visible administrator authorization:

```sh
teaway auth register
teaway auth status
```

teaway does not silently replace a root-owned helper during an upgrade — the machine-level trust decision must stay visible. Your awake state and any scheduled shutdown are unaffected by the upgrade. See the [Upgrade guide](/guides/upgrade) for full details.

## Recovery

If teaway reports an unexpected state, start with the three read-only inspection commands before taking any corrective action:

```sh
teaway status
teaway shutdown status
teaway auth status
```

Common recovery situations:

- **`needs-recovery`** in `teaway status` — a transaction journal remains after an interrupted operation. Run `teaway off` or `teaway shutdown cancel` (whichever matches the state) and re-check. Do not delete state files manually.
- **`external`** in `teaway status` — `disablesleep` is live but teaway has no ownership record. `teaway off` will leave the external value unchanged by design. Use `/usr/bin/pmset -g` to inspect what set it, and resolve ownership before using `teaway on`.
- **`needs-repair`** in `teaway auth status` — the helper/sudoers rule pair is incomplete or version-mismatched. Re-run `teaway auth register` or `teaway auth unregister` as appropriate.

See the [Recovery guide](/guides/recovery) for a complete walkthrough of each state and its resolution path.
